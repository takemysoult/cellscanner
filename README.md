# Ячейка по штрихкоду

Пикнули сканером штрихкод — приложение нашло, в какой ячейке должен лежать товар,
и **сразу напечатало стикер 40 × 58 мм**: крупно номер ячейки, под ним артикул.
Ни одного клика в обычном ходе работы.

```
                  ночью, по расписанию
  [1С: УТ] ──COM──> [ПК с платформой] ──загрузка──> [Яндекс.Диск]
                                                          │ скачивание
                                                          ▼
  [сканер] ──штрихкод──> [складской ПК: локальная копия] ──> [Xprinter]
```

Машинам не нужно видеть друг друга по сети, а сервер 1С не задействован вообще —
там ничего не создаётся и не меняется. При сканировании интернет тоже не нужен:
приложение читает базу со своего диска.

## Почему через файл, а не напрямую в 1С

На складском ПК стоит **тонкий клиент** 1С, а в его дистрибутив не входит
`comcntr.dll` — COM-соединение оттуда невозможно в принципе, сколько ни
регистрируй. OData у базы не опубликована (на сервере `Serv1C` Apache отдаёт
дефолтную страницу Debian).

Поэтому данные забирает машина, где полная платформа есть: раз в сутки она
выгружает срез «штрихкод → ячейка + артикул» в файл `cells.db` и кладёт его в
общую папку. Складское приложение читает только файл.

Это оказалось не компромиссом, а выигрышем:

* на рабочих местах не нужна ни платформа 1С, ни лицензия, ни совпадение
  разрядности, ни связь с сервером;
* поиск идёт по индексу SQLite — мгновенно, вместо ~30 секунд только на
  установку COM-соединения;
* сеть отвалилась — склад продолжает работать на вчерашней копии;
* весь срез занимает ~5 МБ (23 706 штрихкодов, 23 494 размещения).

Плата одна: данные обновляются раз в сутки. Для этой базы это приемлемо —
размещения меняются редко.

Прямой режим (COM) в приложении остался: он нужен машине, которая делает
выгрузку, и включается в настройках.

## Что нужно

**На складском ПК** (рабочее место со сканером):

* Windows;
* сканер, работающий как клавиатура (HID keyboard-wedge) — почти все проводные
  модели так и работают «из коробки»;
* принтер этикеток (Xprinter по кабелю), установленный в Windows;
* интернет (для обновления базы; при сканировании не нужен).

**На машине выгрузки** (у вас — рабочий ПК):

* полная **64-битная** платформа 1С с зарегистрированным COM-коннектором;
* Python **3.10 x64** и venv проекта;
* пользователь 1С с правом **«Внешнее соединение»**.

## Установка

На складском ПК — установщиком `CellScanner-Setup-<версия>.exe`, Python там не
нужен. На машине выгрузки — из исходников:

```bat
py -3.10 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
```

Запуск из исходников: `run.bat` (без консоли) или `run_console.bat` (с журналом
в окне).

## Как файл попадает на склад

Транспорта два, переключаются в **Настройки → Источник данных**.

### Яндекс.Диск (основной)

ПК с платформой 1С загружает `cells.db` на Диск, складской ПК его скачивает.
Машинам **не нужно видеть друг друга по сети** — достаточно интернета: ни общих
папок, ни учётных данных Windows, ни настроек рабочей группы. Сервер 1С не
задействован вообще.

Десктопный клиент Яндекс.Диска не нужен — работаем напрямую с API по HTTPS.

Файл лежит в *папке приложения* на Диске (`app:/cells.db`): токен даёт доступ
только к ней, к остальным файлам Диска — нет.

### Общая папка (запасной)

Обычный путь, видимый обеим машинам: папка на складском ПК, на рабочем ПК или на
любом сетевом ресурсе. Работает без интернета, но требует, чтобы машины видели
друг друга по сети.

### Что общего

В обоих случаях приложение читает **локальную копию** базы
(`%LOCALAPPDATA%\CellScanner\cells.db`), а не файл в облаке или в общей папке.
Поэтому при сканировании ни сеть, ни интернет не нужны: пропал интернет —
склад продолжает работать на последней скачанной базе.

Скачанный файл **проверяется до подмены** рабочей копии: недокачанный или битый
не затрёт вчерашнюю рабочую базу.

## Выгрузка и доставка — два разных шага

Интернет может отвалиться, а складской ПК — быть выключен, поэтому шаги разделены:

1. **Выгрузка** собирает снимок локально, в
   `%LOCALAPPDATA%\CellScanner\export\cells.db` на ПК с платформой 1С.
2. **Доставка** отправляет готовый файл (на Диск или в общую папку).

Если доставить не удалось, выгрузка возвращает код **2** — это не потеря данных:
снимок готов и лежит на месте. Задача-досыл раз в час повторяет только доставку,
**без повторного обращения к 1С**. Появится связь — файл уедет сам.

Коды возврата `export_cells.bat`: `0` — выгружено и доставлено, `1` — выгрузка
не удалась, `2` — выгружено, но не доставлено (повторится).

## Токен Яндекс.Диска

Нужен один раз, и один и тот же вводится на обеих машинах. Токен выдаёт Яндекс —
приложение только хранит его зашифрованным (DPAPI), как и пароль 1С; в журнал он
не попадает.

1. Откройте <https://oauth.yandex.ru> → **Создать приложение**.
2. Платформа — «Веб-сервисы», Redirect URI —
   `https://oauth.yandex.ru/verification_codes`.
3. Доступы: «Яндекс.Диск REST API» → **«Доступ к папке приложения»**. Доступ ко
   всему диску выдавать не нужно.
4. Скопируйте ClientID созданного приложения и откройте:
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=ВАШ_CLIENT_ID`
5. Подтвердите доступ — Яндекс покажет токен.
6. Вставьте его в **Настройки → Источник данных → Токен Яндекс.Диска** и нажмите
   **«Проверить Яндекс.Диск»**: приложение покажет, отвечает ли Диск и лежит ли
   там файл.

Ту же справку выдаёт кнопка **«Как получить?»** рядом с полем токена.

## Настройка выгрузки (машина с платформой 1С)

1. **Настройки** → «Источник данных»: «Напрямую из 1С (COM)», транспорт —
   «Яндекс.Диск», вставить токен. Вкладка **1С** → база, пользователь, пароль,
   «Проверить подключение».

   Подключение к 1С можно перенести из соседнего ZZap Sync одной командой
   (заберёт и пароль):

   ```bat
   .venv\Scripts\python tools\provision.py --share "app:/cells.db"
   ```
2. Проверка:

   ```bat
   tools\export_cells.bat
   ```

   В `%LOCALAPPDATA%\CellScanner\logs\export.log` должно появиться
   `Снимок собран за N с` и `Доставлено: …`.
3. Две задачи в «Планировщике заданий» (уже зарегистрированы):
   * **CellScanner - vygruzka yacheek iz 1C** — ежедневно в 04:00,
     `cmd.exe /c "<папка проекта>\tools\export_cells.bat"`;
   * **CellScanner - dosyl na skladskoy PK** — раз в час,
     `cmd.exe /c "<папка проекта>\tools\export_cells.bat" -deliver`.

Выгрузка занимает 40–95 секунд, из них большая часть — установка COM-соединения.
Досыл, когда доставлять нечего, отрабатывает мгновенно.

Задачи запускаются **только когда пользователь вошёл в Windows** (пароль учётной
записи в планировщике не сохранялся). Если ПК на ночь не выключают и сеанс не
завершают — этого достаточно; иначе в свойствах задачи включите «Выполнять вне
зависимости от регистрации пользователя», Windows запросит пароль.

Весь вывод `export_cells.bat` пишется в `logs\export.log`, поэтому сбой ночного
запуска виден даже если он произошёл до старта Python.

## Настройка складского ПК

1. После установки приложение само откроет **Настройки**.
2. Вкладка **Источник данных**: «Локальная база», транспорт — «Яндекс.Диск»,
   вставить **тот же токен**, что и на машине выгрузки. Частота проверки
   обновлений — 60 минут. Нажать «Проверить Яндекс.Диск».
3. Вкладка **Печать**: принтер подбирается автоматически при первом запуске.
   Если в списке не тот — **«Найти принтер этикеток»**, затем **«Пробная печать»**.
4. Сохраните. В шапке появится «● База: выгрузка от …», курсор встанет в поле
   сканера — можно пикать.

Приложение всегда читает **локальную копию** (`%LOCALAPPDATA%\CellScanner\cells.db`),
а из общей папки файл только копируется целиком. Поэтому обрыв сети посреди смены
ничего не ломает, а SQLite не работает по SMB.

## Горячие клавиши

| Клавиша | Действие |
|---------|----------|
| `Enter` | поиск (его шлёт сам сканер после штрихкода) |
| `F2`    | напечатать выбранную ячейку ещё раз |
| `F3`    | открыть стикер в PDF (когда принтера нет под рукой) |
| `F5`    | обновить базу (в режиме COM — переподключиться) |
| `Esc`   | вернуть курсор в поле сканера |

## Ручной ввод артикула

Под полем сканера есть второе поле, поменьше: туда набирается артикул с коробки,
когда штрихкода нет или он не читается. Enter — и дальше всё как при сканировании:
поиск, ячейка на экране, печать (если включена автопечать).

Отличия от сканирования:

* ищет **строго по артикулу**, а не «сначала штрихкод, потом артикул»;
* курсор после поиска остаётся в этом же поле — обычно за одним набранным
  артикулом следует другой. `Esc` возвращает к сканеру;
* защита от двойного срабатывания не применяется: повтор здесь — осознанное
  действие человека, которому нужна ещё одна этикетка.

Артикул ищется без учёта регистра. Если под одним артикулом несколько позиций,
собираются ячейки всех — как и при запасном поиске по сканированному коду.

## Откуда берётся ячейка

Запросы выверены на живой базе «Торговля 2025» (УТ 11, `Srvr=Serv1C;Ref=ut2025`).
Разведка метаданных показала:

| Объект 1С | Роль |
|-----------|------|
| `РегистрСведений.ШтрихкодыНоменклатуры` | измерение `Штрихкод` → ресурс `Номенклатура`. 23 706 записей, дублей штрихкодов нет |
| `РегистрСведений.РазмещениеНоменклатурыПоСкладскимЯчейкам` | измерения `Номенклатура`, `Склад`, `Помещение`, `Ячейка`; ресурс `ОсновнаяЯчейка`. 9 213 записей — **это и есть «где товар должен лежать»** |
| `РегистрНакопления.ТоварыВЯчейках.Остатки` | **пуст**: склады включены в режиме «адресное хранение справочно», фактических остатков по ячейкам нет — поэтому источник ячейки именно регистр размещения |

Логика поиска одинакова для обоих источников:

1. штрихкод ищется среди штрихкодов номенклатуры;
2. если не найден и включена галка «искать по артикулу» — то же значение
   пробуется как артикул (на коробках часто напечатан он);
3. найденные размещения фильтруются по складам из настроек, дедуплицируются
   (регистр разбит ещё и по помещениям) и сортируются: основная ячейка первой.

Правила отбора живут в одном месте (`build_placements`), поэтому прямой запрос и
локальная база отвечают одинаково. Это проверено сверкой: **155 кодов, 154
ответа совпали полностью**. Единственное расхождение — мелкая подпись
(наименование) у артикула `6203`, под которым в базе несколько разных позиций:
1С и снимок выбирают из них по-разному. Ячейки и артикул совпали везде. Таких
спорных артикулов 198 из 8 061 (2.5%), и затрагивают они только подпись при
поиске по артикулу — при обычном сканировании штрихкода наименование точное.

Тексты запросов правятся во вкладке **Запросы** (для прямого режима) — код
трогать не нужно. Требования к своему запросу: плейсхолдер `{ШТРИХКОД}`
(подставляется как строковый литерал 1С, кавычки экранируются) и порядок колонок
`Ячейка, Артикул, Наименование, Склад, ОсновнаяЯчейка`.

## Если ячеек несколько

Один товар может быть размещён в нескольких ячейках (в базе встречается до 4 —
например, подшипник `6203`). Тогда:

* по умолчанию печатается первая (основная) и в статусе выводится
  предупреждение «есть ещё N ячеек»;
* список альтернатив показан на экране — выберите строку и нажмите `F2`;
* если печатать вслепую не хочется, снимите в настройках галку «Если ячеек
  несколько — печатать основную»: приложение будет ждать выбора;
* чаще всего неоднозначность убирается фильтром по складам во вкладке
  **Запросы** (например, оставить только `Квант (Новые) 3 этаж`).

## Стикер

40 × 58 мм, книжная ориентация. Сверху вниз: склад мелко → **ячейка максимально
крупно** → линия → артикул → наименование мелко. Склад и наименование
отключаются в настройках; ячейка и артикул печатаются всегда.

Размер шрифта не задан числом, а подбирается под ширину этикетки, поэтому и
`А12`, и `2-3-3-11-1-1` занимают её целиком. Если в одну строку получается мелко,
номер ячейки переносится по дефису — двумя строками шрифт выходит крупнее.

Печать идёт напрямую, без диалога Windows. Тот же код рисует превью на экране и
PDF, так что напечатанное совпадает с показанным.

### Если Xprinter печатает не в масштабе

Приложение просит у драйвера страницу ровно 40 × 58 мм. Если драйвер такого
размера не знает, он подставит ближайший — стикер обрежется или уедет. Лечится в
свойствах принтера Windows: создать пользовательский размер бумаги 40 × 58 мм и
сделать его размером по умолчанию для этого принтера.

## Сборка установщика

```bat
powershell -ExecutionPolicy Bypass -File packaging\build.ps1
```

PyInstaller собирает `CellScanner.exe` (onedir, без консоли), Inno Setup 6 пакует
его в `dist\CellScanner-Setup-<версия>.exe` и кладёт копию на рабочий стол.

Внутри установщика: приложение со всеми зависимостями (Python на целевой машине
не нужен) и среда выполнения **Microsoft Visual C++** — без неё Qt5 на чистой
Windows падает с `DLL load failed while importing QtCore`. Галки при установке:
ярлык на рабочем столе и автозапуск при входе в Windows.

Настройки и локальная база живут в `%LOCALAPPDATA%\CellScanner` и при удалении
программы не стираются.

Версия задаётся в одном месте — `MyAppVersion` в `packaging\installer.iss`.

Два подводных камня, уже учтённых в файлах: `build.ps1` и `installer.iss`
сохранены в **UTF-8 с BOM** — без BOM Windows PowerShell 5.1 читает `.ps1` как
ANSI и падает на разборе, а ISCC выдаёт кракозябры в окне установщика.

## Разработка

```bat
.venv\Scripts\python -m pytest tests -q
```

92 теста покрывают чистую логику: экранирование и сборку запроса, разбор ответа
1С (дедуп, фильтр по складам, сортировка), запись и чтение снимка, обновление из
общей папки, настройки и шифрование пароля, раскладку стикера и вывод в PDF,
самодиагностику окружения. Живая 1С для них не нужна.

| Файл | Ответственность |
|------|-----------------|
| `app/snapshot.py` | схема локальной базы, запись выгрузки, чтение, доставка (`push`/`pull`) |
| `app/yadisk.py` | клиент Яндекс.Диска: загрузка, скачивание, проверка токена |
| `app/query.py` | тексты запросов, экранирование, `{ШТРИХКОД}` |
| `app/onec.py` | COM-соединение, поиск, правила отбора ячеек, разбор ошибок 1С |
| `app/diagnostics.py` | самодиагностика: разрядность, регистрация коннектора, версии платформы |
| `app/config.py` | настройки, источник данных, строка соединения, список баз 1С |
| `app/label.py` | геометрия стикера и подбор шрифта |
| `app/printing.py` | поиск принтера, прямая печать, PDF |
| `app/gui/` | окно сканирования, настройки, рабочий поток |
| `tools/export_cells.py` | выгрузка из 1С в `cells.db` |

Про COM важно помнить: он апартаментно-потоковый. Всё общение с 1С живёт на одном
рабочем потоке (`app/gui/worker.py`), а перед `CoUninitialize` COM-объекты
обнуляются и делается `gc.collect()` — иначе их финализация после деинициализации
COM роняет процесс.

## Журнал

`%LOCALAPPDATA%\CellScanner\logs\scanner.log` — состояние источника данных,
результаты поиска, ошибки печати, отчёт об окружении при каждом запуске. Ротация
по 1 МБ, 3 файла. Пароль в журнал не попадает: текст ошибок 1С чистится от
`Pwd=`/`Usr=` перед записью.

Если приложение показывает ошибку, кнопка **«Подробности»** выводит полный текст
и отчёт об окружении прямо в окне — на складской ПК за журналом ходить не нужно.
